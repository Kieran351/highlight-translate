# 划词翻译源语言检测方案调研

调研日期：2026-08-01

## 1. 调研目标

为 Highlight Translate MVP V1 选择完整选区的主要源语言识别方案。

已确认的产品规则：

1. 一次划词产生的完整选区只识别一种主要源语言。
2. 目标语言固定为简体中文。
3. 识别为中文时，不调用 DeepSeek，翻译卡片原样显示选区内容。
4. 识别为非中文时，将完整选区发送给 DeepSeek 翻译为简体中文。
5. 中英混合选区不按语言片段拆分。

因此，本次检测发生在调用模型之前，必须能够在浏览器本地完成，否则无法满足“中文选区不调用模型”的要求。

## 2. 市面产品的主要做法

### 2.1 浏览器内置语言检测

Chrome 为扩展提供 `chrome.i18n.detectLanguage(text)`。该接口使用 Chrome 内置的 CLD 检测文本，可以返回最多三个候选语言、各自占比和 `isReliable` 可靠性标记。它从 Chrome 47 起可用，Chrome 99 起支持 Promise。[Chrome i18n 官方文档](https://developer.chrome.com/docs/extensions/reference/api/i18n)

Chromium 的设计说明明确将它定位为“扩展检测一段用户文本的主要语言”，典型用途正是翻译页面中的局部文本，并指出本地检测可避免在用户真正要求翻译前把文本发给第三方。[Chromium 设计说明](https://www.chromium.org/developers/design-documents/extensions/proposed-changes/apis-under-development/language-detection/)

局限：

- 短文本可靠性低于长文本；Chromium 建议较长文本更可靠。
- 混合文本会返回候选占比，但产品仍需决定哪个候选算主要语言。
- 检测模型和结果可能随 Chrome 更新变化。

### 2.2 浏览器内置本地 AI 检测模型

Chrome 138 起在桌面提供 `LanguageDetector` API。它在客户端运行，返回按置信度排序的候选语言；模型首次使用时可能需要按需下载。[Chrome Language Detector 官方文档](https://developer.chrome.com/docs/ai/language-detection)

官方同时说明：

- 仅支持桌面 Chrome，不支持移动端。
- 首次创建检测器可能需要用户激活并等待模型下载。
- 极短短语和单词准确率较低，应设置置信度阈值。
- API 不能在 Web Worker 中使用。

该方案比传统 CLD 暴露了更明确的概率排序，但需要额外处理能力检测、模型下载、初始化和运行上下文。

### 2.3 插件自带本地检测器

部分工具在应用内部集成检测器或字符规则，避免依赖翻译服务。

- `TinyLD` 是纯 JavaScript、本地运行、无 API 调用和运行时依赖的检测器，支持浏览器，并声称针对短文本进行了优化。[TinyLD 官方仓库](https://github.com/komodojp/tinyld)
- `franc` 是浏览器可用的字符 n-gram 检测器，可按版本支持 82、186 或 419 种语言；但项目文档明确提醒，语言覆盖越多，短文本越容易混淆，默认不足 10 个字符时返回未知。[franc 官方仓库](https://github.com/wooorm/franc)
- Saladict 的公开实现包含按中文、英文、日文假名、韩文等字符范围判断文本的规则，适合快速筛选，但不是完整的统计语言识别。[Saladict 语言检查源码](https://raw.githubusercontent.com/crimx/ext-saladict/dev/src/_helpers/lang-check.ts)

优点是完全离线、行为可测试和跨浏览器；代价是增加包体、依赖维护和算法调参责任。

### 2.4 交给翻译服务自动检测

DeepL、Google、Microsoft 等翻译服务通常允许省略源语言，由服务端自动检测完整输入。例如 DeepL 浏览器扩展会自动检测源语言，用户设置目标语言。[DeepL 扩展官方帮助](https://support.deepl.com/hc/en-us/articles/4407580229522-Translate-with-the-browser-extensions)

“划词翻译”也曾先请求翻译服务，再根据检测出的源语言决定是否切换目标语言；后续版本增加内置检测，以避免中文到中文请求后再发起第二次请求。[划词翻译 v7 更新日志](https://www.hcfy.ai/en/docs/log/v7/)

该模式是传统翻译产品的常见做法，但不适合本项目当前约束：为了知道文本是不是中文，必须先把文本发送出去，纯中文也会调用服务。

### 2.5 多检测源聚合

Easydict/Raycast-Easydict 提供多个语言检测源，并使用用户的偏好语言提高歧义文本的判断优先级。其说明也承认短词可能同时属于多种语言，例如英文词可能被识别为荷兰语。[Raycast-Easydict 官方仓库](https://github.com/tisfeng/Raycast-Easydict)

这类聚合能提高覆盖面，但需要多个网络服务或平台能力，不符合 MVP 的简单性和“检测阶段不上传文本”目标。

## 3. 三个最优候选方案

以下恰好列出三个符合当前项目约束的最优方案，并按推荐顺序排列。

### 方案一：`chrome.i18n.detectLanguage` + 极短文本本地规则兜底

**推荐等级：第一名，推荐用于 MVP V1。**

流程：

1. 对完整选区做最小规范化，只去除两端空白，不拆分语言片段。
2. 调用 `chrome.i18n.detectLanguage(text)`。
3. 若结果可靠，取占比最高的语言作为完整选区的主要源语言。
4. 将 `zh`、`zh-CN`、`zh-TW` 等中文结果统一归类为中文。
5. 若结果不可靠或未知，只对明显的短文本使用 Unicode 脚本规则兜底：
   - 含日文假名则优先视为日文；
   - 含韩文字符则视为韩文；
   - 只包含汉字、中文标点、数字和空白时视为中文；
   - 其他情况视为未知。
6. 中文原样展示；非中文调用 DeepSeek；未知按产品规则单独处理。

优势：

- 完全本地，无额外网络请求。
- Chrome 扩展原生 API，接入代码少。
- 无额外模型下载和第三方运行时依赖。
- 能获得候选语言、占比和可靠性，不只是简单正则判断。
- 与“完整选区只判断一个主语言”的产品规则直接匹配。

风险：

- 短词、品牌名、代码和高度混合文本仍可能不可靠。
- 检测结果会随 Chrome 内部 CLD 更新发生小幅变化。
- 必须明确定义未知结果的行为。

适用结论：当前项目只运行在本人桌面 Chrome，且 MVP 重视低复杂度和隐私，因此该方案综合最优。

### 方案二：Chrome `LanguageDetector` 本地模型 + `chrome.i18n` 回退

**推荐等级：第二名，适合准确率验证阶段或 V2。**

流程：

1. 检测 `LanguageDetector` 是否可用。
2. 模型可用时，通过它获取按置信度排序的候选语言。
3. 最高候选超过设定阈值时作为主要源语言。
4. API 不可用、模型未就绪或置信度不足时，回退到 `chrome.i18n.detectLanguage`。

优势：

- 本地运行，不上传待检测文本。
- 返回标准化置信度排名，便于设置不确定阈值。
- Chrome 官方为翻译前语言识别设计的现代 API。

风险：

- 要求桌面 Chrome 138 或更高版本。
- 首次使用可能需要模型下载和用户激活。
- 不能在 Service Worker 中直接使用，需要安排在页面、扩展文档或其他适合的上下文中。
- 极短文本仍不准确，官方建议返回未知。
- 对单人 MVP 来说，引入的初始化和回退逻辑相对重。

适用结论：若后续实测发现 CLD 对真实选区的误判率不可接受，可以将该方案作为增强层，而不是 MVP 的首选依赖。

### 方案三：插件自带纯 JavaScript 检测器 + Unicode 规则

**推荐等级：第三名，适合需要跨浏览器或固定算法版本时。**

实现可选择 TinyLD 一类面向短文本的本地检测器，并对中文、日文假名、韩文等独特脚本增加确定性规则。若使用 `franc-min`，必须接受其对短样本容易混淆的已知限制，并缩小候选语言集合。

优势：

- 完全离线，行为不随 Chrome 内部实现变化。
- 可固定依赖版本并建立自己的回归测试集。
- 未来迁移到 Firefox 或其他环境时复用度较高。
- 可根据本项目只需判断“中文或非中文”的特点做定向优化。

风险：

- 增加扩展包体和供应链依赖。
- 需要维护语言代码映射、升级、安全审查和准确率测试。
- 短文本、中文与日文汉字、品牌名仍无法被通用统计库完美识别。
- 当前仅支持本人 Chrome，没有足够收益抵消维护成本。

适用结论：如果未来需要跨浏览器，或必须保证相同输入在不同 Chrome 版本中输出完全相同的检测结果，再考虑该方案。

## 4. 方案对比

| 维度 | 方案一：Chrome CLD + 规则 | 方案二：LanguageDetector + 回退 | 方案三：自带检测器 |
| --- | --- | --- | --- |
| 本地运行 | 是 | 是 | 是 |
| 中文检测前上传文本 | 否 | 否 | 否 |
| MVP 实现复杂度 | 低 | 中高 | 中 |
| 首次模型下载 | 无 | 可能需要 | 随扩展安装 |
| 额外运行时依赖 | 无 | 无第三方依赖 | 有 |
| 短文本可靠性 | 需规则兜底 | 官方仍提示较低 | 取决于库和规则 |
| 混合文本主语言 | 候选占比最高 | 最高置信度候选 | 取决于库 |
| Chrome 版本要求 | Chrome 47+ | Chrome 138+ | 现代浏览器 |
| 跨浏览器 | 否 | 否 | 较好 |
| 行为版本稳定性 | 可能随 Chrome 变化 | 可能随模型变化 | 可固定版本 |
| 当前项目匹配度 | 最高 | 较高 | 中等 |

## 5. 最终推荐

MVP V1 推荐使用：

> `chrome.i18n.detectLanguage` 负责完整选区的主要语言检测，极短或不可靠结果使用少量 Unicode 脚本规则兜底。

推荐原因：

1. 它是 Chrome 专门为扩展检测局部文本语言提供的原生能力。
2. 完全本地，满足中文选区不调用模型的约束。
3. 无模型下载、第三方依赖和额外权限负担。
4. 返回候选占比和可靠性，足以实现“整块只识别一种源语言”。
5. 若未来准确率不足，可以平滑升级为 `LanguageDetector` 主检、CLD 回退，不需要改变后续翻译流程。

建议的数据结构：

```ts
type DetectedSourceLanguage = {
  language: string | "unknown";
  isChinese: boolean;
  confidence?: number;
  reliable: boolean;
  method: "chrome-cld" | "unicode-fallback" | "unknown";
};
```

## 6. 下一项待确认

采用推荐方案后，仍必须确认“不可靠或未知”的行为：

- 保守跳过模型并原样显示；或
- 将完整选区发送给 DeepSeek，让翻译请求同时承担语言判断。

该决定影响短单词、品牌名、代码和少量混合文本的体验，是下一项阻塞性产品规则。
